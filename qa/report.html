CRITICAL BUG-01 · ลบใบเบิกแล้วสต็อกเพิ่มผี (คืนของที่ไม่เคยถูกตัด)

ตาราง stock_out มีคอลัมน์ stock_deducted ที่บอกว่าใบนั้น ตัดสต็อกจริง หรือเป็นใบ sync ย้อนหลังที่ไม่ได้ตัดสต็อก แต่ฟังก์ชันลบที่ปุ่มบนหน้าเว็บเรียกใช้ กลับคืนสต็อกกลับทุกใบโดยไม่ดู flag นี้เลย

// parts/includes/StockService.php:1000  — deleteStockOut()
foreach ($detail['items'] as $item) {
    $this->db->prepare('UPDATE products SET quantity = quantity + ? WHERE id = ?')
        ->execute([(int) $item['quantity'], (int) $item['product_id']]);   // ← คืนทุกใบ ไม่เช็ค stock_deducted
}

สิ่งที่ยืนยันว่านี่คือบั๊ก ไม่ใช่การออกแบบ: ระบบมีฟังก์ชันตรวจสำเร็จรูปอยู่แล้ว (production_stock_out_was_deducted_row()) และโค้ดลบอีก 2 จุดในระบบเดียวกัน เช็คถูกต้องแล้ว — มีเฉพาะ path ที่ผู้ใช้กดจากหน้าเว็บเท่านั้นที่ลืมเช็ค

// parts/includes/production_sync.php:1016 — ทำถูกต้อง
$returnStock = production_stock_out_was_deducted_row($headerRow);
if ($returnStock) { /* คืนสต็อก */ }

// parts/includes/production_sync.php:1086 — ทำถูกต้องเช่นกัน
$returnStock = production_stock_out_was_deducted_row($dedSt->fetch());

stock_deducted = 0  →  145 ใบ   ← 81% ของทั้งหมด กดลบเมื่อไหร่สต็อกเพิ่มผีทันที

HIGH BUG-02 · แก้จำนวนใบเบิกแล้วสต็อกติดลบได้

เมธอด updateStockOutSingle() ตรวจของคงเหลือ นอก transaction ด้วย SELECT ธรรมดาที่ไม่มี FOR UPDATE แล้วหักสต็อกด้วย SQL ที่ ไม่มี guard — ต่างจากเมธอดพี่น้องทุกตัวในไฟล์เดียวกัน

// parts/includes/StockService.php:920 — ปัจจุบัน (ไม่มี guard)
UPDATE products SET quantity = quantity - ? WHERE id = ?

// stockOutItem():490, stockOutBySet():432, deleteStockIn():861 — ทำถูกต้อง
UPDATE products SET quantity = quantity - ? WHERE id = ? AND quantity >= ?   +  เช็ค rowCount()===0 แล้ว throw
ผลทดสอบจริง (รันใน transaction แล้ว rollback — ไม่แตะข้อมูลจริง): 
ก่อน       : P00001 qty = 92
หลัง       : qty = -50   (rowCount=1)   ← SQL แบบปัจจุบัน ยอมให้ติดลบ
แบบมี guard : qty = 92   (rowCount=0)   ← SQL ที่ควรเป็น ระบบจะ throw error

HIGH BUG-03 · ไฟล์ cron เปิดให้เรียกจากเว็บได้โดยไม่ต้อง login

MEDIUM BUG-05 · อัปโหลดโลโก้เป็นไฟล์ SVG ที่ฝัง script ได้ (Stored XSS)

appearance.php:47 อนุญาตนามสกุล svg และ save_upload() ตรวจไฟล์ SVG เพียงว่า 4096 ไบต์แรกมีข้อความ <svg เท่านั้น — ไฟล์ SVG ที่มี <script> ฝังอยู่จึงผ่านได้

// config.php:714
if ($ext === 'svg') {
    if (stripos(file_get_contents(...,0,4096), '<svg') === false) return null;  // ← ตรวจแค่นี้
}

uploads/.htaccess ปิดการรัน PHP ไว้แล้ว (ดีมาก) แต่ไม่ได้กัน SVG — เมื่อเปิด URL ของไฟล์ตรงๆ เบราว์เซอร์จะรัน JavaScript ในนั้นภายใต้โดเมนของระบบ ซึ่งขโมย session ของผู้ใช้คนอื่นได้ · ความเสี่ยงถูกขยายโดย BUG-04 เพราะผู้ใช้ทั่วไปก็เข้าหน้านี้ได้

แนวทางแก้: ตัด svg ออกจากรายการที่อนุญาต (ใช้ PNG แทน) หรือ sanitize เนื้อไฟล์ก่อนบันทึก

MEDIUM BUG-08 · parts/sftp.json เก็บรหัส FTP จริงไว้ใน webroot

LOW BUG-10 · dead code

StockService::getRecentMovements() (บรรทัด 203) ไม่มีใครเรียกใช้ทั้งโปรเจค · stockOutByWebhook() (บรรทัด 715) มาร์ค @deprecated แล้วและไม่มีทางเรียกถึง เพราะ endpoint ปิดไปแล้ว — ควรลบทิ้งเพื่อลดภาระการดูแล

ส่วนที่ตรวจแล้วไม่พบปัญหา

  • CSRF ครบถ้วน 100% — สแกนทุกไฟล์ที่รับ POST ในระบบหลัก ไม่พบไฟล์ไหนที่ขาด csrf_check() เลย
  • ไม่พบช่องโหว่ SQL injection — ทุก query ใช้ prepared statement · ส่วน ORDER BY ที่รับค่าจากผู้ใช้ใช้ whitelist ($sortSql[$sort]) · LIMIT cast เป็น (int) ก่อนต่อสตริงทุกจุด
  • ทุกหน้าบังคับ login — ไฟล์ที่ไม่เรียก require_login() ตรงๆ ล้วนเรียกผ่าน require_can() (ซึ่งเรียก require_login() ต่อ) หรือเป็นแค่หน้า redirect
  • part_stock_bridge.php เขียนถูกต้องทั้งไฟล์ — ใช้ AND quantity >= ? + เช็ค rowCount() + ตั้ง stock_deducted = 1 ตอนตัดสต็อกจริง (เป็นตัวอย่างที่ควรยึดเป็นแบบ)
  • uploads/.htaccess ปิดการรัน PHP ในโฟลเดอร์อัปโหลดไว้เรียบร้อย
  • Webhook เดิมที่ไม่มี auth ถูกปิดแล้ว — api/webhook-stockout.php คืน HTTP 410
  • ทางลัด Tom ถูกจำกัดเฉพาะ localhost แล้ว — ใช้บน production ไม่ได้
