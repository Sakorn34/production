# ADR 0002 — ทะเบียนสินค้ากลางอยู่ที่ `biton_stockparts.stock` จุดเดียว

- **สถานะ:** Accepted (ตกลง 13 ก.ค. 2569)
- **ขอบเขต:** `finishgoogs_ma_update/` (ฝั่งเขียน/sync), ตาราง `stock` เป็นของทีมระบบสต็อกอะไหล่

## บริบท

ก่อนหน้านี้ระบบทะเบียนเครื่องมีตารางของตัวเองชื่อ `shared_assets` ไว้เก็บสำเนาข้อมูลเครื่องสำหรับแชร์ให้ระบบอื่นดู ควบคู่ไปกับตาราง `stock` ที่ทีมสต็อกอะไหล่ดูแลอยู่แล้วในฐานข้อมูล `biton_stockparts` — ทำให้มีทะเบียนสินค้า **สองชุดคู่ขนาน** ที่ต้องคอยซิงก์ให้ตรงกัน เสี่ยงข้อมูลเพี้ยนและงานซ้ำซ้อน

คอมเมนต์หัวไฟล์ `share.php` ยืนยันการตัดสินใจนี้ตรงๆ:
> `ข้อมูลรายการสินค้าเก็บที่ stock ที่เดียว (ตกลง 2026-07-13 — เลิกใช้ shared_assets แล้ว)`
> `ห้าม ALTER เพิ่มฟิลด์ในตาราง stock — เค้าโครงเป็นของระบบสต๊อกอะไหล่ของทีม`

## การตัดสินใจ

1. **ยกเลิกตาราง `shared_assets`** เลิกเก็บสำเนาข้อมูลเครื่องซ้ำ — ใช้ `biton_stockparts.stock` เป็นทะเบียนสินค้ากลางแหล่งเดียว (single source of truth)
2. **`finishgoogs_ma_update` เป็นฝ่าย sync เข้า ไม่ใช่เจ้าของ schema** — ทุกครั้งที่บันทึก/แก้ไขเครื่องผลิตใหม่ใน `assets` ระบบจะเรียก `share_upsert_asset()` (`config.php:474`) เขียนเข้า `stock` ให้อัตโนมัติ แต่**ห้ามแก้โครงสร้างตาราง `stock`** เพราะเป็นของทีมระบบสต็อกอะไหล่ (แม้ว่าในทางเทคนิคจะเป็นฐานข้อมูลคนละตัวกับ `parts/` ก็ตาม — `biton_stockparts` เป็นฐานข้อมูลกลางแยกจากทั้งสองระบบ)
3. **มีเครื่องมือตรวจ/แก้ข้อมูลไม่ตรงกัน** — หน้า `share_admin.php` ใช้ `share_reconcile_index()`/`share_reconcile_list()` เทียบ `assets` กับ `stock` และ sync ซ้ำเป็นรายตัวหรือทั้งหมดได้ (ผ่าน `share_sync_all_from_production()`)
4. **นำเข้าข้อมูลเก่าจาก CSV ได้** ผ่าน `share_import_basic_csv()` — ต้องรับมือกับความไม่สม่ำเสมอของ format วันที่จาก AppSheet export (ปนกันระหว่าง DD/MM และ MM/DD, มี AM/PM) ใช้ `share_detect_fmt()` ตรวจรูปแบบจากข้อมูลจริงในไฟล์แทนการ hardcode รูปแบบเดียว

## ผลกระทบ

- ลดความเสี่ยงข้อมูลสองชุดไม่ตรงกัน แต่แลกกับการที่ `finishgoogs_ma_update` **พึ่งพา schema ของทีมอื่น** — ถ้าทีมสต็อกอะไหล่เปลี่ยนโครงสร้างตาราง `stock` โดยไม่แจ้ง ฟังก์ชัน sync ในฝั่งนี้อาจพังแบบไม่มีการแจ้งเตือนล่วงหน้า
- การ sync เป็นแบบ **fail-soft** (ดู [ADR 0003](0003-transaction-locking-strategy.md)) คือถ้า sync พลาดจะไม่ทำให้การบันทึกเครื่องหลักล้มเหลวตาม แต่ต้องอาศัยหน้า `share_admin.php` ในการตรวจจับและแก้ไขย้อนหลังด้วยมือ
